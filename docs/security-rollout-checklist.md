An actual separate-connection local test demonstrates a lock-order inversion for **direct privileged role DELETE versus the admin suspension RPC**: direct deletion can lock a tuple before its trigger takes the role advisory lock, while the RPC takes the advisory lock first. PostgreSQL detects the deadlock and aborts one transaction. Do not treat direct deletes, profile/Auth cascades, bulk maintenance or disabling triggers as safe lifecycle operations; an independently reviewed maintenance/deletion protocol and bounded, idempotent retries are required. The test does not prove all deadlocks or concurrent paths safe.

The final local draft explicitly revokes service-role privileges on review-only private audit records, non-service RPCs and directly restricted notes/classroom/test tables, including when permissive service-role default grants exist. Code tables also have RLS enabled with no ordinary-user policies. `node scripts/test-review-privileges.mjs` verifies a synthetic full-chain catalog under permissive service defaults, fixed function search paths and selected grants. This is defense in depth, **not** a sandbox for owners, superusers, BYPASSRLS, inherited roles, arbitrary SQL, disabled triggers, existing unrelated grants or a leaked service key. Earlier public baseline tables and real project default privileges/role membership require a separate catalog review. Supabase commonly gives service roles privileged capabilities; test actual grants and ingress, not assumptions based on PGlite. No local test can make an exposed privileged credential safe.

## Connected practice memory

Within an authenticated app instance, a student's in-progress session and unsaved attempts now survive the provider remount caused by same-user token re-verification. The queue pauses immediately on an Auth event and resumes only after profile/role re-verification; one in-memory worker serializes retries. Account changes and sign-out discard that memory. An already in-flight HTTP request cannot be recalled, so server-side authorization remains essential. This reduces one loss mode, **not durable recovery**: reload, browser crash, tab close, app unmount or sign-out can still lose unsaved work; before-unload warnings are not guaranteed. No detailed student answers are newly stored in browser storage. Any durable outbox requires an explicit shared-device/privacy/retention decision, quota and failure handling, account isolation, multi-tab coordination and security review before use.

## Isolated test gate (requires separately approved project)

1. Verify exact project identity and isolation. Review migration order, current data, object ownership, existing grants, default privileges, role memberships and exposed schemas before applying anything. Investigate the existing project's conflicting branch status using dashboard logs separately; never assume it is safe to reset or retry.
2. Use distinct synthetic admin, teacher, student and parent accounts, including multi-role and unrelated accounts. Disable public signup; configure redirect allowlists, isolated email/SMTP and non-production keys. No real children's data.
3. Review/apply the full migration chain in order **only after authorization**. Inspect effective grants and RLS as anon, authenticated, service and owner roles. Verify all endpoints, security-definer owners/search paths, missing/extra policies, direct table/column/sequence grants, default privileges, `SET ROLE`/inheritance and exposed schemas. Do not put service keys in browser code.
4. Exercise valid/invalid sign-in, logout, token refresh and expiry, role loss and profile load failure, recovery links, replay/expiry and separate-device behavior. Verify callbacks, emails, rate limits and session isolation.
5. Test tutor linking, revocation/relink and student/parent/teacher suspension with separate real connections and tokens. Check active and archived memberships, code retirement, retained notes and assignments, regrant blocking, rollback on audit failure and already-returned data. Include stale repeatable-read/serializable snapshots, lock timeouts and deadlock retries. Verify direct privileged paths and cascade deletion independently.
6. Test classroom trusted gateway identity, API permissions, rate limits, abuse/flood controls, code expiry/rotation, occupancy and races; test homework request retries, fences, quota exhaustion and cancellations; verify student result storage and network failures. Check logging, secrets, monitoring and retention.
7. Record security/privacy sign-off, backup/restore and retention/deletion decisions, rollout/rollback and incident procedures. Obtain separate production authorization before any live change.

Local regression commands: `npm run test:review-policies` and, after installing its optional local embedded PostgreSQL dependency, `npm run test:review-concurrency`. These use ephemeral synthetic databases and do not substitute for isolated Supabase tests or independent review.

## Unwired recovery and evidence prototypes

`src/practice/reviewAttemptOutbox.ts` is an opt-in-only IndexedDB prototype; the app never opens it. It stores the full submitted attempt and student UUID on the device, not encrypted. Account namespaces do not stop someone with same-origin/device access from reading records. Transactions bound entries to 50 per owner and compare the complete wire payload before treating a duplicate as identical or acknowledging it. Fake-IndexedDB tests exercise reopening, collision, multiple connections, quota, corruption, storage failure and explicit owner discard. An isolated Chromium smoke test also covers reopen, two-page conflict and exact acknowledgement; see `scripts/test-review-outbox-browser.mjs` (it only accepts a local Vite origin and uses optional scratch browser dependencies). The user has agreed in principle to explicit device opt-in, with a shared-device warning and a way to remove local data. `src/practice/reviewOutboxCoordinator.ts` is an unwired local draft for durable-write-first handoff, per-owner Web Locks coordination across participating tabs, owner re-verification, cancellation fencing, exact-ack retry and explicit discard even after opt-out; it does not itself provide consent UI, durable consent state or cross-tab consent revocation. In-flight requests and transactions cannot be recalled, and locks cannot coordinate nonparticipating code. Before integration, add informed UX, device-wide opt-out and lifecycle cleanup, verified real Auth, quota remediation and real-browser/private-mode/crash tests, and resolve remaining privacy/retention questions. Acknowledge only after the backend has confirmed the exact payload. Clearing data may lose unsaved work and cannot recall an in-flight request. No lesson draft or unsent current session is persisted by this prototype.

`server/practice-evidence-review.ts` is an unrouted, single-process, in-memory **review prototype** for single-choice server-side issuance and comparison. It is not an API and no deployed service, real Auth, durable evidence, achievement or streak uses it. Client-facing objects omit answer, explanation, generator seed and template ID, and tests cover owner isolation, one accepted answer, duplicate IDs, expiry, distinct prompts, and actual generator output. The host would have to derive identity from verified Auth; trusting a caller-supplied owner would be insecure. Question text/options and public template code can still reveal answers; correct answers do not prove a child worked independently or mastered a topic. It does not implement trusted lesson completion, coverage/mappings, anti-abuse, real retention/deletion, transactional persistence, distributed concurrency or replay controls. Never use its review result as a verified award or payment entitlement.

## Parent review draft

`#/parent` remains unavailable while `TEST_ACCOUNT_MODE` or `PARENT_REVIEW_ENABLED` is off. The dormant UI verifies the Auth user and parent role, displays linked active students, reduced recent attempt summaries, and parent-published tutor notes, and clears its view on Auth changes. Scores are explicitly labelled unverified. Requests check the current parent role, link and student role; already delivered responses cannot be recalled and auth callbacks are not an instant remote revocation signal. The RPC limit is 30 attempts, but the latest local review migration limits published notes to 100.

**Important:** the initial live schema permits linked parents to read complete `exercise_attempts.result` via direct table select. The unapplied dashboard review migration changes that policy locally: a parent-only role gets summaries, while the student and an independently linked teacher keep raw access. Subscription-based full access is deferred, so no parent subscription entitlement is recognized. Multi-role accounts retain independent role access. Real-project grants, policies and bypasses must be audited before relying on this boundary. Teacher links and parent links may also expose retained records again upon relinking. Before use, confirm subscription entitlement requirements separately, audit effective grants/policies and role combinations, review consent, retention, accessibility and shared devices, and test real concurrent authorization/session behavior. The draft does not provision Auth users or establish parental authority.

## Durable evidence pilot (not an award system)

`202612070001_evidence_pilot_review.sql` is an unapplied, service-only local draft. It stores single-choice sessions, issued public prompts/options, correct and selected answers and server timestamps in private tables. Its RPCs serialize through the student role lock, require READ COMMITTED, limit active sessions/questions, accept exact answer retries, and finish only after ten distinct answered prompts. They do not accept the existing client-scored attempts. Answers and rows are not returned to ordinary users by these RPCs. The pilot is not used by any UI, streak, badge or achievement.

`server/practice-evidence-pilot-gateway.ts` is unrouted. Its core validates bounded requests, requires injected verified authentication, trusted network and distributed rate-limit dependencies, constructs the public response from a whitelist, and obtains all new question material from an injected server generator. A narrow server-only RPC adapter is included. **No runtime wiring, deployed trusted generator, dedicated distributed limiter, approved curriculum scope, student-facing recovery protocol, endpoint monitoring, real Auth verification or real-project tests exist.** The database trusts the actor and question supplied by the privileged service; a caller who obtains that credential or controls the service could forge evidence. Ordinary generated questions may expose or imply their own answers; correctness is not proof of independent work or mastery. A request ID scopes a question retry but is not bound to curriculum (the pilot has no curriculum scope). Rate and retention limits for finished/expired sessions, session recovery across devices, deletion/anonymization of identifiable records, answer retention and private-key/worker access must be designed before use. The separate local scoring prototype and this pilot cannot be treated as verified achievement or streak events.

`node scripts/test-evidence-pilot-policy.mjs` exercises synthetic access and limits; `node scripts/test-evidence-pilot-concurrency.mjs` tests selected retries, conflicting answers, finish, role suspension and isolation with real separate local PostgreSQL connections. The full-chain catalog test includes the new service-only functions and private tables under permissive service defaults. These tests do not establish real Supabase ownership, grants, Auth or production safety.

The isolated Chromium smoke test now also exercises the outbox coordinator using actual Web Locks across two browser pages. Opt-in UX, cross-tab opt-out and lifecycle integration are still absent, so no browser app opens the outbox.
