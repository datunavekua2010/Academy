# Accounts and tutor–student links: local implementation and release review

**Status:** Review features remain disabled and are not production-ready. `TEST_ACCOUNT_MODE` is still true. The initial schema, tutor-notes and classrooms migrations have been applied only to the authorized test project; other review migrations are not applied there or on the existing live project. See [test-project-progress.md](test-project-progress.md).

## Account access

In a future connected build, the student sign-in uses academy-provisioned email/password credentials. The tutor gate now has its own sign-in form and sign-out control. Password success does not grant teacher access: the tutor workspace separately calls `auth.getUser()` and checks the caller's current teacher role and profile before loading data. Missing roles fail closed; a denied account can sign out. Error messages do not expose Supabase details and password fields clear after submission. Auth events cause verification again and invalidate stale teacher loads. The student provider now invalidates stale profile loads and rechecks the student role and profile on Auth events including token refresh, rather than trusting an unchanged user ID. Database RLS is still the authorization boundary; role changes are not instantly pushed to a dormant UI, and Auth event checks do not replace policy checks.

There is **no** public sign-up, invitation acceptance, parental account flow or automated Auth-user provisioning. A later review-only SQL draft can provision an Academy profile for an already-existing Auth user; it is not enabled or deployed. A review-only password recovery request and reset screen has been added behind `VITE_PASSWORD_RECOVERY_ENABLED=true`, but test mode still prevents the recovery client from being created and the flag defaults off. The production recovery flow needs real Supabase email/SMTP testing, account-enumeration protection, rate limits, exact redirect allowlists and hash-router/callback verification; see below. Do not distribute passwords through chat. Public registration must be disabled at Supabase itself if using administrator-provisioned accounts; hiding the UI is not a security control. Review session storage on shared devices, signing out and data privacy. Never put service-role secrets in client code.

## Tutor links

The current design chooses academy-admin-managed linking; classroom invite codes do **not** create a tutor link or add a parent approval step. `202611280001_admin_teacher_links_review.sql` is a local draft depending on the initial schema and the review-only classroom migration. `admin_establish_teacher_link` requires an authenticated, academy-provisioned `admin` role, a currently valid teacher role and student role, and an opaque external authorization-record reference. Only authenticated users have execute privilege; the function checks the actual `auth.uid()` and does not accept an admin identity from the caller. It inserts the link and a private audit row in the same transaction, or returns false for an existing link without inventing a new audit event. Direct writes to links and audit rows remain denied to ordinary authenticated users. An existing link grants broad access under the initial RLS; this operation must therefore only be used after the academy's independent authorization process. The reference is **not proof of authorization or consent** and must be an opaque, non-identifying internal ID, not a name, email, student information or an explanation.

The initial link draft refuses to relink a pair with retained classroom memberships when the link is absent, to avoid silently resurrecting hidden memberships. The subsequent revocation draft below supplies a cleanup path. Neither supplies an admin UI, creates user accounts, captures consent, removes roles, or protects operations performed outside these functions by privileged administrators. No current role or relation grants are loosened. A reference also cannot establish age, parental authority, notice or lawful basis. Define and verify those requirements and records before handling real children’s data.

**Release blockers:** independently review the unlink/role-removal lifecycle, retention, audit and re-link rules. Ensure there are no alternative privileged mutation paths that bypass its locking protocol and decide what happens to assignments, notes and reports after revocation; see the limitations below. Review all existing RLS, role provisioning and administrative permissions. Confirm how to safely handle pre-existing links and audit history. Define who is an admin, how their roles are provisioned/removed and how records are reviewed. Independent security/privacy review and real multiconnection Supabase tests are required.

## Revocation draft

`202611290001_teacher_link_revoke_review.sql` depends on the previous classroom, capacity, code and admin-link migrations. Its admin-only, `auth.uid()`-checked function removes that pair's memberships from all the tutor's classrooms, including archived classes, and then removes the tutor–student link in the same transaction. It records an opaque internal request reference and aggregate removal count in a private audit table, leaves other teachers' memberships and parent links alone, and is idempotent. It also cleans retained memberships for an already-missing link. A later independently authorized relink **does not restore the removed classroom memberships**; the student must be added or join anew. This is not a UI and is not deployed. Reference IDs must not contain personal details; the administrator must independently verify authority for the action.

For participating paths the lock order is pair advisory lock, then classrooms in stable ID order, then membership/link operations. Establish, classroom direct-add and code redemption acquire the same pair lock before class locks and recheck their authorization. A real local PostgreSQL multi-connection test forces both orderings of redeem vs. revoke, add vs. revoke, establish vs. revoke, and the final-place race. It checks that the competing transaction actually waits. Run it with `npm install --prefix .scratch/postgres embedded-postgres@18.7.0-beta.19` followed by `node scripts/test-teacher-link-concurrency.mjs`; binaries and ephemeral database stay in ignored `.scratch`. `node scripts/test-teacher-link-revocation-policy.mjs` tests authorization, audit rollback, parent/other-tutor isolation, archived membership cleanup, relinking, notes and attempts. These tests use synthetic data, not real Supabase.

**Important limits:** privileged direct database writes and role deletion/reinstatement can bypass the pair protocol. A subsequent local role-lifecycle draft below adds constrained suspension and reinstatement guards; it is not deployed and does not implement complete historical cleanup or account deletion. The review-only `202611300001_teacher_write_lock_review.sql` adds the same pair lock and a post-lock authorization recheck to lesson-note writes and direct assignment writes. It addresses the tested race orderings, but it is not deployed and does not guard privileged operations that disable/bypass triggers or other unreviewed workflows. New reads after committed unlink are denied by RLS/current link checks, but already returned data, open UI state, screenshots and external exports cannot be recalled; the app has no real-time purge guarantee. Assignments, attempts and lesson notes are retained, not destroyed. Under the existing policies, a later tutor relink can make retained assignments/attempts and tutor notes visible again, and published notes can reappear for the parent. Relinking is an explicit authorization action, but these effects need a product, retention and privacy decision before release. Student-facing old assignments and parent links are not removed by this operation. The database must also have a reviewed way to resolve incomplete role revocation and legacy data safely.

## Password recovery draft

Student and tutor sign-in screens offer an optional recovery request only in a connected build with the recovery flag on. The dedicated Supabase client uses PKCE and a one-time code, stores the verifier in browser localStorage for same-browser email links, keeps the recovery session in memory under a random per-page client/broadcast key, and never replaces the normal signed-in app session. The latest request is the only reliable pending link on a browser; a link opened on another device/browser, a reload after exchange, blocked storage or an expired/used link requires a new request. Only a confirmed `PASSWORD_RECOVERY` SDK event plus matching verified user enables password change. The callback is processed once outside React effects and its query/fragment is removed from browser history before exchange; a site-wide `no-referrer` meta tag reduces referrer leakage. The code can still appear in upstream request logs before the app loads, email scanners can interfere with single-use links, and this does not replace hosting/header/log review. Password reset does not by itself guarantee immediate revocation of all existing sessions; define and test the Supabase session policy.

To test after a separate isolated project is identified, configure that project's Auth SMTP, appropriate anti-enumeration/rate controls and exact redirect allowlist for `https://<test-site>/<path>?recovery=1`, with no broad production wildcard. Ensure the actual Supabase email template returns the PKCE code and preserves the recovery marker. Use only test accounts and a test-only build with `VITE_PASSWORD_RECOVERY_ENABLED=true` and `TEST_ACCOUNT_MODE` off, never real-user data. Confirm new/old passwords, expired/reused links, scanners, cross-tab/device behavior, wrong-account sessions, repeated requests, network failure and redirect behavior in actual browsers. Test browser privacy mode and blocked storage, account-enumeration and throttling server-side, and avoid logging codes, passwords, sessions or recipient emails. Return to default-off for real environments until review, integration testing and separate release authorization.

A separate test project was subsequently identified and authorized. Three migrations were applied there, and rollback-only synthetic SQL tests were run; Auth settings were not changed and no synthetic accounts remain. See [test-project-progress.md](test-project-progress.md).

## Assignment and lesson-note write coordination

`202611300001_teacher_write_lock_review.sql` depends on the initial schema, notes and all link/classroom/revocation review migrations. It serializes note creation, edits, publication and deletion, and assignment inserts, updates and deletes, against revocation of the same tutor–student pair. The SQL checks the current signed-in teacher, active teacher/student roles and link again after obtaining the pair lock, and holds existing role/link rows against deletion until commit. Assignment author and student become immutable through updates; moving an assignment to another student requires a new assignment. RLS remains in force. The trigger deliberately rejects any assignment write without a matching authenticated tutor, including unimpersonated service-role/administrator imports: an independently reviewed import/maintenance mechanism is needed instead of bypassing it. Bulk writes involving different pairs can deadlock under conflicting order; PostgreSQL aborts a transaction, so callers need safe retry and idempotency handling.

The order is significant: a write which acquired the pair lock first can commit before revocation; if revocation acquired it first and commits, the subsequent write fails or affects no rows. This does not recall already returned data or cancel operations committed before revocation. Historical assignments, attempts and notes remain retained, and their relink behavior remains a release decision. Reads, privileged workflows, role revocation and other future tables need separate coordination and review. This migration is not applied remotely.

`node scripts/test-teacher-write-lock-policy.mjs` checks RLS, role and link checks, identity immutability, direct helper denial and fail-closed unimpersonated writes. `WRITE_LOCK_REVIEW=1 node scripts/test-lesson-notes-policy.mjs` reruns the existing publication, author, parent and revision cases with the complete review chain. `node scripts/test-teacher-write-lock-concurrency.mjs` uses local PostgreSQL separate connections and checks both race orders for note create/edit/publish/delete and assignment create/update/delete, plus stale repeatable-read snapshots. Install the optional local test dependency as in the revocation section. These are synthetic local tests, not proof of Supabase/PostgREST configuration or every possible interleaving.

## Role suspension and reinstatement: review-only draft

`202612020001_role_lifecycle_review.sql` has been applied **only to synthetic local databases**. It depends on the initial schema and the local notes, classrooms, teacher tests, capacity, codes, link establishment/revocation, teacher write-lock and homework migrations. It does not change live Supabase or enable real authentication. It provides a narrow, audited admin RPC to revoke one `teacher`, `student` or `parent` role. It does not revoke `admin`, allow an admin to suspend their own account, create/regrant roles, collect parental consent, ban a Supabase Auth account, invalidate its sessions or delete personal data. An opaque external reference is an operational audit identifier, not evidence of consent or authorization. Repeated revocation of an absent role returns false and produces no audit event, although it advances a private concurrency epoch; an audit failure rolls back the role change.

This is **suspension with retained relationships**, not bulk deletion: teacher/student and parent/student links, class memberships, invites, assignments, attempts, notes, saved tests and other history remain in the database. A suspended student loses role-based access to their practice data, and linked teachers/parents lose access to that student's data in the revised RLS helpers and parent-note RPC. A teacher whose role is removed loses teacher-scoped reads; a suspended parent loses parent-scoped reads. An account can have multiple roles, so removing one role does not remove its other roles or self-profile visibility. Student-visible homework already published remains visible to an active student when the teacher role is suspended. Open or previously returned data cannot be recalled; sessions are not invalidated. Reinstating the student can expose their own retained data again. After explicit relinking, historic assignments and notes can reappear to authorized tutors and parents. Whether these retention and re-exposure rules are appropriate requires product, legal and privacy decisions.

A role regrant is not implemented by this migration. A trigger on direct privileged role inserts fails closed if regrant would silently restore retained teacher links, parent links, classroom memberships, or an unrevoked teacher classroom code. Cleanup is explicit: existing `admin_revoke_teacher_link` removes one pair and its active/archived class memberships; `admin_revoke_parent_link` removes one parent link; `admin_retire_suspended_teacher_codes` retires all unrevoked codes for a suspended teacher, including archived classes. The latter two are admin-only, idempotent and audited. Code retirement is only allowed after teacher role removal, and a retired code does not revive after regrant. A new link or classroom membership still requires its own authorization. A later local draft adds admin-only parent-link creation and guarded role restoration, but no parent UI, admin relationship-inventory UI, or complete regrant workflow exists; authorized operators would need independently reviewed privileged procedures to discover which retained links need cleanup. If a hidden membership has no link, the existing pair cleanup still removes it. Regrant checks are deliberately conservative: even a duplicate privileged `INSERT ... ON CONFLICT DO NOTHING` may fail while relationships exist. Direct privileged writes, disabled triggers, future link-creation paths and cascades must be independently reviewed and brought under the same protocol; never bypass the guard as a rollout shortcut.

The suspension function locks a role-specific advisory key, verifies the administrator under a row lock and removes only the target role; it does not acquire a changing set of pair locks. Existing link establishment, lesson-note/homework writes and code redemption hold/recheck participant role rows, so participating writes that win the lock finish before removal, and those losing it fail or affect no rows. New triggers lock/recheck the student role for attempt inserts and the teacher role for classroom and saved-test writes; classroom-member removal now uses the pair lock and role checks. Role insertion/deletion, the admin suspension operation and code retirement also update a private per-role epoch in the same transaction: this forces tested stale repeatable-read reinstatement, suspension and retirement snapshots to fail rather than act on an outdated role state. Service code issuance still uses the service RPC authorization path; the classroom trigger checks the owner role, not service impersonation. The epoch and audit tables contain identifying metadata and foreign-key restrictions that can prevent profile/Auth deletion: a separately reviewed deletion, anonymization, backup and audit-retention procedure is mandatory. Concurrent bulk operations can deadlock; applications need bounded, idempotent retry, and not all privileged operations or interleavings are covered.

Tests: `node scripts/test-role-lifecycle-policy.mjs` applies the full local review chain and covers role/parent/code authorization, audit rollback, retained data, hidden access, cleanup and guarded regrant. `node scripts/test-role-lifecycle-concurrency.mjs` uses optional local embedded PostgreSQL (installation above) and separate connections to force both orderings for role removal against student attempts, link establishment, homework and note writes, classroom creation and member removal, saved tests and service code issuance; it also covers stale repeatable-read regrant, suspension and code retirement, and code retirement vs regrant. Existing note, classroom-code and saved-test suites also pass with the complete role lifecycle chain when run with `ROLE_LIFECYCLE_REVIEW=1`. These tests use synthetic data, not actual Supabase or real accounts. They do not establish real Auth-token revocation, all reads or all role/link races, migration compatibility with production data, deletion correctness, service ingress security, or a lawful retention policy. Independent security/privacy review and authorized isolated-project integration remain release blockers.

## Further local review drafts: parent links, restoration, and stale pair snapshots

`202612030001_parent_link_review.sql` adds an authenticated-admin-only parent/student linking RPC and replaces the parent unlink RPC. The caller must independently validate parental authority and lawful basis; an opaque reference is not evidence of either. These operations retain historical records and a newly authorized parent link may expose them, including published lesson notes. Pair advisory locks plus private per-pair epochs coordinate both operations and force the tested stale repeatable-read snapshots to abort. An attempted duplicate link or absent unlink does not create a new audit event, although it advances the epoch. Cleanup works even if a participant role is suspended. Both profiles must exist. Direct privileged writes, cascades and future creation paths remain outside this protocol. Epoch and audit FKs/metadata complicate deletion and require retention/privacy review. Later local drafts add disabled Auth signup, parent sign-in/dashboard, and an admin UI, but no production enrollment or consent/authority-verification system. See `accounts-parent-launch-readiness.md`.

`202612040001_role_regrant_review.sql` adds a separate authenticated-admin-only `admin_restore_academy_role` for one parent, student or teacher role. It does not create or unban an Auth account, grant admin, restore relationships or retire codes. Only a role with a latest audited suspension may be restored; new role provisioning and untracked direct deletions require a separate procedure. Existing guards reject retained relationships/memberships/unrevoked codes; the operator must explicitly resolve these first. Already-active roles return false, while successful restoration and audit are atomic. Role regrant can reveal the student's own historical data; subsequent explicit re-link can expose retained records. Reference IDs are not proof of authorization. A full safe regrant/inventory/deletion workflow and independently reviewed legal/privacy rules are still missing.

The earlier `202611290001_teacher_link_revoke_review.sql` now includes a private teacher/student pair epoch for admin establish/unlink. A reproduced stale repeatable-read transaction previously could re-establish a link after a newer committed unlink; the epoch now makes the tested stale establishment and stale unlink abort with serialization failure. This does not fence arbitrary privileged SQL or every race. The additional per-pair epoch holds identifying IDs, adds FK restrictions, and needs retention/deletion review. Deadlocks remain possible, especially direct privileged role deletes vs. admin suspension, so callers need bounded safe retry and independently reviewed maintenance procedures.

`node scripts/test-parent-link-policy.mjs` and `node scripts/test-role-restore-policy.mjs` test local permissions, rollback, cleanup and regrant guards. `node scripts/test-parent-link-concurrency.mjs` tests selected pair and suspension races and stale snapshots in separate-connection local PostgreSQL; the teacher and role concurrency suites cover the new fences and restore/suspend races. The full-chain catalog suite tests grants with deliberately permissive service defaults. These drafts remain unapplied; these checks are not a substitute for isolated real-account or independent security/privacy review.

## Existing-Auth-user profile provisioning: local draft

`202612050001_profile_provision_review.sql` adds an authenticated-admin-only RPC to atomically create an Academy profile and exactly one teacher, parent or student role for an **already existing** Auth UUID; a student must also have an explicit grade. It cannot create users, passwords, emails, admin roles, parent/student or teacher/student links, consent records, payment access or invitations, and will not overwrite existing profiles. The operator is responsible for independently verifying that the Auth identity and requested role/grade are correct and authorized. The opaque reference is not proof of identity, parental authority or lawful basis. An Auth account existing does not imply email verification, good standing or that it has been unbanned. Do not use real children's data before independent privacy and legal review.

The admin supplies a random request UUID and must retry the **exact same normalized payload and key** after an uncertain response. A different payload with the same key fails. A different key cannot overwrite an existing profile; a lost/uncertain request must not be abandoned and replaced without the later review-only reconciliation/fencing procedure. A matching retry reports that the original operation committed, not that the profile/role is still active now. Request and target advisory locks, the database uniqueness constraints and admin-role row lock coordinate the tested concurrent calls. The audit record, role, grade and profile commit atomically; an audit failure rolls all back. The private ledger retains target/admin IDs and a SHA-256 digest of a canonical payload; this is not anonymization and must not be treated as secret. Metadata/FKs complicate data deletion, rate/volume limits and retention/cleanup are unresolved, and stale transactions must retry safely. Later local drafts add a disabled admin UI and reconciliation RPC; neither is deployed or independently reviewed.

`node scripts/test-profile-provision-policy.mjs` and `node scripts/test-profile-provision-concurrency.mjs` exercise authorization, exact retry/conflict, atomic rollback, selected request/target/admin-role races and stale snapshots with synthetic local databases. Actual `auth.users` table ownership and `FOR SHARE` privileges, active/confirmed target account status, project default grants, Supabase Admin API provisioning, token behavior, and deletion/cascade behavior need separate review and isolated-project testing. The draft is unapplied and must not be used to provision real accounts.
