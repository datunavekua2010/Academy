### Repository implementation completed

- The Google callback now distinguishes successful identity sign-in followed by an unavailable proof from an identity sign-in failure; both failure screens link back to the public homepage, without granting any role. This is local code only and does not repair the staging proof endpoint. `user_roles` accepts only student, parent, teacher and admin; no generic member role is assigned by this change.
- Student and parent Google signup forms call separate atomic self-enrollment RPCs after the session-bound Google proof. Enrollment preserves existing profile names, does not restore revoked roles, and does not create parent-child links. A parent adult checkbox is an attestation, not proof of age, consent, or authority.
- Parents can submit, list and cancel link requests. Parent-facing request RPCs now require Google proof **directly**, even if the existing global `has_role` helper is not method-aware. A different authorized admin must independently verify authority and enter an internal reference before approval uses the existing link lifecycle. The request alone confers no child access.
- Proof Worker routes reject requests lacking Cloudflare edge metadata or bearing Worker-subrequest headers; the existing fail-closed IP/account limiter stores keyed hashes rather than raw IPs. This is defense in depth, not proof that the Cloudflare ingress configuration is correct and not a replacement for WAF/provider limits.
- `supabase/review/release/202612120001_signup_additive.sql` is a generated, transactional **additive install candidate**. It adds proof, enrollment and application objects, but does **not** replace `has_role`, existing RLS, or other existing functions. Its four private DB gates (`proof`, `authorization`, `enrollment`, `parent_link`) default false; enrollment and link operations additionally require both `proof` and `authorization`. The `authorization` gate is an operator attestation, not an automatic check that enforcement is installed. An owner-only bounded cleanup function removes expired challenges, proofs and old limiter rows; an operator must actually schedule it. A collision or missing dependency aborts the transaction. No existing profile, role, link or student record is removed. The candidate has been self-reviewed and locally tested, **not independently reviewed or tested on hosted Supabase**.
- `wrangler.signup-staging.toml` targets only the owner's `axiomtest` staging Worker; it has no production routes, credentials, or proof-enabled flag. Use explicit `--config wrangler.signup-staging.toml --keep-vars` for any future staging deployment so it does not target production or delete dashboard variables. The example file is also kept for reference. Neither file is itself a deployment.

## Rollback and scope

With only this additive candidate installed and all gates false, existing policies are unchanged. To stop new signup/application operations after a staging test, a trusted DB operator may set the `enrollment`, `parent_link`, and `authorization` rows to false; this does not delete or roll back roles or links already created. Do not blindly disable `proof` after global method enforcement is active: that would deny existing student/parent sessions. Preserve data, identify affected sessions and use the separately reviewed enforcement rollback plan. The generated candidate is not a substitute for tested backup/restore or migration-history reconciliation.
