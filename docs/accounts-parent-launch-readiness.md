# Accounts and parent access — local implementation and release gate

**Review only; features remain disabled.** This is not production approval. The user authorized synthetic tests and migrations only in the separate test project. The first three migrations have been applied there; the remaining chain has not. See [test-project-progress.md](test-project-progress.md). No real children's data was used. Subscriptions and payments are deferred.

## Local flow

1. An adult can request an Auth account using `#/account/register` (for themselves or on behalf of their child). `VITE_ACCOUNT_SIGNUP_REVIEW=true` and real account mode are required; both are off by default. The signup client uses Supabase PKCE, an exact same-origin callback, a verifier in localStorage and an isolated in-memory Auth session. The email link must be opened in the same browser; later requests replace the earlier verifier. The callback strips URL parameters before exchanging, verifies the user and confirmed email, and signs out the temporary session. It never signs into or replaces the main app account. The form never assigns roles or links; an adult's checkbox and an Auth ID do not prove age, identity, parental authority or consent.
2. The account owner signs in with the ordinary student, parent or teacher entry point. `#/account/status` displays their own confirmed Auth ID for a private support workflow. An existing Auth account alone grants no Academy role. Without an approved Academy role, the respective workspace denies access. A separately authorized operator must verify identity/authority and lawful basis outside this app; never rely on a self-asserted checkbox, UUID, email, or a reference code as proof.
3. Disabled `#/admin` uses the normal authenticated client and the database's admin-only RPCs; no service key is in browser code. An operator can create an Academy profile for an existing Auth user and establish/revoke a parent/student link. The latest local profile RPC requires a confirmed, non-anonymous, non-deleted, unbanned Auth row at provisioning time and holds a row lock. It does not automatically create student Auth users, verify identity/custody, validate consent or continuously revoke sessions on later bans. It has no administrative user lookup: find/verify the Auth ID via an approved support process.
4. Profile and parent-link requests use a caller-supplied random request ID. The UI freezes the original inputs after submission, supports exact retry and an explicit resolve-or-fence action, and does not offer a new request in that form until the outcome is resolved. Operators must save the ID and exact payload securely **before** submission: refresh, sign-out, account changes or token refresh can clear the form, and the app deliberately does not save sensitive admin drafts in browser storage. The separate resolver can check a saved ID after reload. A committed result is historical and does not imply the role/link is currently active; an abandoned result fences a late request. Fence and parent-link ledgers have per-admin 30-new-per-10-minute and 10,000-lifetime limits. Exhaustion requires a reviewed maintenance/retention plan, not deleting rows blindly. Only READ COMMITTED transactions are supported. Legacy non-idempotent parent-link RPC grants are revoked in the final local migration; owner SQL, privileged cascades or disabled triggers can still bypass this protocol.
5. The disabled `#/parent` view checks the verified current Auth user and parent role, and fetches only currently linked, active students. The local SQL exposes at most 30 recent unverified attempt summaries and 100 recent parent-published notes from currently linked, active tutors. It does not return answer JSON. The local policies deny a parent-only account direct reads of student profiles, grades, assignments, attempts, raw progress and rewards; an independently held student or linked-teacher role retains its own access. Parent link rows remain visible to their parent. The UI labels scores as unverified; already-received data and screenshots cannot be recalled. Relinking may expose retained published notes and summaries. No subscriber entitlement or full-attempt parent access exists.

## Google account review draft

The Google OAuth option is implemented locally behind `VITE_GOOGLE_AUTH_REVIEW=true`, and is also disabled by `TEST_ACCOUNT_MODE`. The normal connected Supabase client uses PKCE when that flag is on. A fixed same-origin callback is scrubbed before exchange; initiation is allowed only when signed out, and a same-tab pending marker is required. A verified, confirmed Auth user is retained in the normal app session; Google authentication never grants an Academy role or links a child. First-time Google sign-in can create an Auth account if the provider and signup are enabled, including from a sign-in screen. The registration form requires adult acknowledgment, which is **not** proof of age, consent or parental authority. Existing role checks still apply.

This is a review draft, not configured or enabled in Supabase and not tested with a real Google account. Existing password accounts and same-email Google identities may be automatically linked by Supabase depending on provider verification and configuration; review and test actual identity-linking behavior, account recovery and account switching before use. The main session and PKCE verifier use browser storage; shared devices, concurrent tabs, lost verifiers, cancellation, token/session revocation and redirect/log leakage need review. A locally stored pending marker and preflight session check do not establish race-free account switching across tabs. Restrict redirects and do not enable for real users before independent security/privacy review.

For an isolated test only, the project owner will need to create a Google Cloud OAuth web client, set its authorized redirect URI to the **test Supabase project's** Auth callback (`https://wxxgwayrieasrzngpuul.supabase.co/auth/v1/callback`), configure the Google provider in that project's Supabase dashboard, and allow the exact test site's `?google_auth=1` callback in test Auth settings. The Google OAuth consent screen and test-user eligibility must also be configured as appropriate. Put the Google client secret directly into the Supabase dashboard, never in the browser, repository, or chat. Use a dedicated synthetic/controlled Google account and test project only. The preview URL, provider and redirects have not yet been configured; no Google login link is ready.

## What must happen before real use

- **The existing live baseline still allows linked parents direct access to full attempt JSON.** The restricted policies and all other review migrations are unapplied. Do not create real parent links or enable this dashboard until the complete migration chain, effective RLS, grants, service/owner privileges and all alternate exposure paths have been reviewed and tested in isolation. Other privileged roles and existing policies can change the outcome.
- Continue only in the approved isolated Supabase test project with synthetic accounts. Verify project identity, backup/rollback, current migration history and branch health before further changes. Inspect actual `auth.users` fields, function ownership and row-lock privileges; the local tests use a synthetic schema. The existing project's branch-list status previously reported `MIGRATIONS_FAILED`, while detail reported `ACTIVE_HEALTHY`; inspect the cause separately.
- Agree and independently review lawful basis, age/guardian verification, notices, parental authority, data minimization, support workflow, retention/deletion, account recovery and incident response. Admin and link request ledgers store identifiers and digests, with restrictive FKs; they complicate deletion. Digesting identifiers is not anonymization. Parent-child relinking re-exposes retained data. Auth or role suspension does not recall already returned data, and existing tokens may remain valid until their configured expiry/revocation.
- Configure and verify Auth email confirmation, public signup settings, redirect allowlists, mail templates, SMTP, abuse controls, CAPTCHA/rate limits, enumeration resistance, password policy, secure headers and callback logging. In particular, test signup with confirmation required, duplicate emails, confirmation links, scanners, expiration, latest-link-only behavior, blocked browser storage, device changes, wrong-account session, recovery, token refresh, sign-out and suspension. A misconfigured Auth project may create an account even if the client rejects an unexpected immediate session. The checkbox is not a consent mechanism. Check that the intended supervised child onboarding is lawful before allowing real student accounts.
- Test admin identity/role loss, delayed requests and resolve fences, explicit relinking, quota exhaustion, grants, parent-only versus multi-role users, revoked links and student/tutor roles through actual Auth/PostgREST and separate real connections. Protect admin accounts with reviewed MFA/session and operator controls. No admin MFA or support/authority-verification system is implemented here. Confirm `READ COMMITTED` and actual `FOR SHARE` privileges, retry/deadlock policy and deletion/cascade behavior. A browser or network error can leave an outcome uncertain.
- Obtain independent security/privacy review and explicit production authorization, then apply migrations/config and enable features only through a staged rollout with monitoring and a tested rollback. `TEST_ACCOUNT_MODE` remains **on**, while `PARENT_REVIEW_ENABLED` and `ADMIN_REVIEW_ENABLED` remain **off**. Signup and recovery also require their own explicit flags. None should be changed for real operation until the release gates above are met.

## Local tests

`npm run test:review-policies` runs synthetic SQL/RLS/catalog suites. `npm run test:review-concurrency` uses optional scratch-only embedded PostgreSQL to force selected separate-connection races. `tests/account-signup.test.tsx` exercises the actual Supabase JS SDK against mocked HTTP; `tests/admin-review.test.tsx`, `tests/account-status.test.tsx`, and `tests/parent-review.test.tsx` test mocked Auth/UI boundaries. These do not prove behavior of a real Supabase project, mail delivery, or all concurrent and privileged paths. Some legacy primitive tests intentionally stop before the final primitive-revocation migration; the full-chain privilege and new wrapper suites cover its final grants.

## Connected-mode implementation update

The app can now be built with `VITE_ACCOUNT_MODE=connected` without editing source. An unset or empty mode uses the isolated preview only in development; a production build without a mode fails closed. `VITE_ACCOUNT_MODE=preview` explicitly selects the isolated preview, and unrecognized values fail closed instead of presenting a sample student as an authenticated user. This changes the current static build unless its deployment sets an explicit mode: do not deploy until a mode and the relevant integrations are configured and tested. `VITE_PARENT_ENABLED=true` and `VITE_ADMIN_ENABLED=true` explicitly expose the parent and operator screens in a connected build, but they are only presentation switches, not authorization. Keep them unset on any environment whose effective policies and RPCs have not been verified. Signup, password recovery and Google still use their separate review flags and server-side prerequisites. This change does not configure or enable any remote service.

The parent dashboard has a refresh control that clears the previously selected child and reloads the relationship-scoped list. It is not a realtime revocation mechanism; already-returned data cannot be recalled. The required summary-only RLS migrations are still unapplied in the test project, whose initial baseline exposes raw attempt JSON to linked parents. Do not enable parent access there before the full policy chain is reconciled and verified. No subscriber entitlements or paid full-attempt path are implemented.
