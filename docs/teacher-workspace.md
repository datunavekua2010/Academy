# Teacher workspace: audit, deployment and remaining work

## Audit

The React/Vite app is hash-routed in `src/main.tsx`. `StudentSessionProvider` uses a public, unauthenticated local-only test account while `TEST_ACCOUNT_MODE` is true. `src/lib/supabase.ts` deliberately suppresses its client in that mode. The future connected student provider verifies the student role. Practice and homework share `PracticeProvider`, `PracticeSession`, `session.ts`, the curriculum and scoring engine. Connected practice inserts a client-scored JSON result in `exercise_attempts`; lesson completion is localStorage only. Connected assignment status now uses assignment-linked client attempts rather than all attempts in the subtopic, but is not authoritative or server verified; legacy demo rows retain their older subtopic-based status. Streaks and achievements currently have no verified awards.

The connected Supabase project was inspected read-only: migration `20261120154717` (`initial_academy_schema`) is deployed; relevant table columns and 18 RLS policies match the initial repository migration. No edge functions were present at inspection. `teacher_students`, `user_roles`, profiles, grades, curriculum, assignments, and attempts already exist. Teachers can read linked student data and create/update/delete their own assignments for linked students. Under the deployed initial policies, direct update can change the student or curriculum to another permitted value and no trusted completion exists. A later local review-only migration prevents changing an assignment’s author/student and coordinates writes with link revocation, but it is not deployed and does not implement trusted completion. Assignment titles/instructions, draft/cancel, optional deadline, notes, interventions and reports do not exist. Do not treat the existing policies or unverified attempts as a complete assignment lifecycle.

## Implemented, not deployed

The `#/teacher` route shows a clearly marked public preview while `TEST_ACCOUNT_MODE` is enabled and there is no Supabase client. It can create and cancel local test assignments for the single test student, and see that student’s local practice attempts. It never queries or writes real account data, has no real role, and does not expose the connected workspace. With test mode disabled, it fails closed unless the existing Supabase client is configured, a real user is returned by `auth.getUser()`, and the caller's own RLS-protected role and profile confirm a teacher. Test student identity never grants authenticated access. Role is rechecked on auth events; server RLS, not the UI, is the security boundary. Scoped, paginated reads use teacher links and show only the teacher's assignments. Student search, grade filter, student details, raw answer-derived accuracy and activity work when real connected teacher data exists. Attempts are explicitly unverified; accuracy is correct answers / all recorded answers (shown only with at least 10 answers), not session score or mastery. Malformed answer records are excluded and reported in analytics. Empty and error states differ.

Parent-update preparation provides unsaved, manually entered fields for a linked student; switching student or navigating away discards the draft. Nothing is sent. No sign-in is exposed and no Supabase client is enabled in test mode. A tutor sign-in form exists in the disabled connected-mode code; see `docs/account-and-linking-review.md`. The local-only test assignment records are unverified and may be cleared by the browser; no real-account writes or automated message delivery are enabled. The test-mode root provides a student/teacher view selector, with the public landing page still available through its link. The remaining sections explain their unavailable status. Existing teacher RLS must be independently reviewed before enabling real users. Persistent reports and delivery, dashboards for parents and intervention tracking are not implemented. Review-only connected homework creation and cancellation are implemented locally behind a disabled flag and require the unapplied migration and independent review described below. Lesson notes are a non-private in-memory preview; connected notes require the reviewed but unapplied migration described in `docs/lesson-notes.md`. No deployed auth, schema, or data changes were made.

## Proposed schema changes for later approval (no migration included)

For the deployed schema, assignment title, instructions and lifecycle need migration; the local review draft below supports published/cancelled (not draft) and a required deadline, with backward-compatible defaults. Require immutable student, author and curriculum references once published; replace unrestricted update/delete with reviewed, constrained transitions that preserve attempt history. Ensure published-only student reads and validate session-to-assignment mapping and server-side completion. Add teacher-authored intervention/notes records only with strict RLS checking teacher ownership and current student linkage, plus audit and retention policy. Report delivery/acknowledgement needs its own reviewed model if persistence is needed. A trusted question/answer and lesson-completion service must precede claims of verified mastery or completion. Existing data needs migration/backfill and rollback planning, plus integration and concurrency/security tests on a dedicated non-production project. No policies should be relaxed.

The connected teacher overview uses the existing schema; separate review-only migrations now exist for notes, classrooms, tests and admin link creation. None should be applied without the separate reviews and authorization described in their feature documents. Keep `TEST_ACCOUNT_MODE = true` until the separate authentication launch is approved. ## Local test homework

In the test teacher workspace, create a titled assignment with an optional instruction, one or more playable curriculum subtopics (including from different units, topics, or grades) and a future deadline for the single local test student. Switch to the matching student homework grade, open it in the existing practice runner and exit or complete a session. Each selected subtopic is saved as a separate assignment sharing the title, instructions and deadline, with independent progress and cancellation. The teacher test profile displays assignment-specific saved session count and score; cancelling hides the assignment from the student while preserving the attempt. Both views use the same browser localStorage keys and do not sync across devices. Reloading a local draft retains its assignment ID. The client-calculated status and score are unverified, are not streak or achievement evidence, and must not be used as a production assessment. Earlier demonstration homework retains its original subtopic-based status.

## Progress reports (read-only, not verified)

The Analytics tab contains the progress-report card; student profiles retain a direct link to the selected student's report. The connected report rechecks the authenticated user, teacher role and current teacher–student link before and after paginated RLS-protected attempt reads. RLS remains the access boundary; no new policy, report table, server function, or account role is created. Reports are temporary React state and are not stored or delivered by Axiom Academy. The existing manual parent-update form remains separate and its private text is not imported.

Dates are inclusive civil days in Asia/Tbilisi (UTC+04:00 since 2014); accepted dates begin in 2015. The JSON `answers[].at` timestamps, correctness flags and question IDs are client-generated and **unverified**. Every saved session for the selected student is fetched and filtered by answer time; `created_at` cannot safely delimit sessions that were saved late. This can become expensive for a long history, and offset pagination is not a transactional snapshot if sessions change concurrently. Duplicate question records within a session are counted once; conflicting or incomplete outcomes are excluded. Unfinished sessions do not appear until saved. Local test reports use the isolated test-practice key, which retains at most 400 sessions. Neither source proves correctness, effort, mastery, complete historical activity or delivery. The schema has no activity-provenance flag to distinguish manually inserted seed/test attempts from real attempts; connected reports must not be treated as production-verified until provenance and trusted scoring are in place. A trusted server-side answer validation and timestamp pipeline, reviewed authorization and dedicated real-account integration testing are required before offering verified or production-authoritative reports.

The complete editable text is copied or sent to an external app only through an explicit user action. WhatsApp uses its documented `wa.me/?text=...` link; Viber uses its documented `viber://forward?text=...` scheme. App availability and actual message delivery cannot be detected, so the UI supplies a manual-copy fallback. The tutor must check the recipient and message; editing can change or remove the included uncertainty disclosure. Sharing exposes the edited text to the chosen external service. No changes to authentication settings, database schema or production deployment were made.

The Analytics tab now offers an expandable progress-report card using the same data source and access checks. After generating and editing a report, the print action opens the browser's print dialog; the user must select “Save as PDF” if supported. Print styles isolate the selected report and its edited message from dashboard navigation and other students' data, and retain the unverified/test-data disclosure. Browser and device print support varies; Axiom Academy does not silently create or send a PDF.

## Connected homework: local review only

`202612010001_homework_review.sql` and `CONNECTED_HOMEWORK_REVIEW` are **not deployed/enabled**. The migration depends on the initial schema plus the review migrations for notes, classrooms, capacity, codes, link establishment/revocation and teacher write locks. It adds title, instructions, published/cancelled state and revision; existing rows receive neutral published defaults. A teacher can atomically publish 1–50 distinct subtopics to one currently linked student with a mandatory future deadline. Each selected subtopic is a separate row and can be cancelled independently. There is no draft, edit, bulk-cancel or trusted completion feature. The server checks that each reference has a registered exercise template; the UI checks the local playable catalogue, whose synchronization with the database still needs integration verification. Direct authenticated assignment mutations are revoked; RPCs check current roles and link after acquiring the same pair lock as revocation. Assignment-author and student remain immutable through the existing trigger. Cancelled rows remain visible to their own currently linked author but not to the student, parent, or another linked tutor; attempts are retained and follow existing attempt-read policies. Link revocation retains student-facing homework and historical records, and a later relink can expose prior history again.

Create retries use a per-teacher request UUID and canonical payload digest; a concurrent identical retry returns the same IDs, while changed content with the same key fails. The private ledger stores SHA-256 of the canonical JSON payload instead of a second copy of student/title/instruction data; this is not encryption or anonymization, and canonicalization and compatibility across database upgrades need review. Before submitting, the UI saves only the random request UUID in teacher-scoped `sessionStorage`, not the student, title, instructions or payload. If storage is unavailable or corrupt it fails closed. An uncertain same-page create can retry the original payload or resolve the request. After same-tab navigation or reload, a recovered ID blocks new operations until resolved. Resolution takes the same request lock as create: it reports `published` if create committed, otherwise writes an `abandoned` tombstone that rejects even a create arriving after the resolution. It returns no student or assignment details, checks the current teacher role and holds that role row while resolving; a revoked role cannot use this endpoint. An uncertain resolution can be retried. A resolved outcome is shown before the teacher refreshes the list. A cancellation is separately idempotent and, after navigation, its status can be checked in the refreshed list.

This is not a universal duplicate-prevention guarantee: session storage may be lost when a tab is closed, cleared, restored differently, or changed; it is not shared as a durable cross-device queue. A new request ID, different tab, or manual SQL/client misuse can still make duplicates. The browser unload warning does not block in-app navigation. Markers and tombstones must not be deleted merely on a timer without a protocol that bounds delayed requests, or old requests could be replayed; there is presently no safe cleanup protocol. The request ledger and quota records are retained indefinitely; they still contain identifying metadata and a digest. Cross-tab behavior, logout/role-removal recovery, retention/privacy rules, abuse controls and request reconciliation remain release blockers. Network failures, revocation and validation errors are deliberately shown as uncertain rather than assuming the operation failed. Concurrent bulk operations and privileged writes need independent review.

Student lists are snapshots with an explicit refresh button, not realtime; a stale tab can start an assignment after cancellation. Existing sessions are not interrupted, and a matching assignment-linked student attempt is allowed even after cancellation: without a trusted start record, the server cannot distinguish a genuine pre-cancellation session from a fabricated later attempt. Scores and session counts are client-supplied and **unverified**, never evidence of completion, mastery, rewards or attendance. Student UI uses 100-point client labels, not verified completion. Student attempts await retry in memory if their save fails; closing or navigating away can lose unsaved attempts. Refresh only replaces the assignment list, not unsaved attempts. User-facing lists already fetched cannot be recalled when links or roles change.

### Request-record limits (local review only)

The draft limits **new committed ledger records** (published batches and abandoned tombstones combined) to 30 per teacher in a fixed 10-minute window and 10,000 per teacher for the lifetime of the ledger. These are provisional engineering safeguards, not approved product limits. A batch of up to 50 assignments uses one slot. Existing-key retries and resolutions, and assignment cancellation, use no new slot. A failed transaction rolls back its slot. A per-teacher row lock serializes competing requests; tested stale repeatable-read snapshots fail rather than exceed the limit. The time window begins when the first request reserves its slot, not necessarily when that transaction commits, so long transactions and bursts across a boundary can yield more than the nominal rate over a rolling ten-minute span. The lifetime ceiling is permanent with this draft; at the ceiling a missing request cannot be fenced, and the UI must remain blocked until an independently reviewed operational resolution exists. The temporary limit likewise delays fencing until a window expires; a delayed create may still win before resolution, in which case resolution reports published. Do not delete tombstones or reset counters casually: a late request might be accepted or the storage bound lost. No cleanup, override or quota-reset workflow exists.

These limits constrain committed rows per account, not traffic or total system size. Failed/invalid requests, retries, concurrent open transactions, multiple teacher accounts and direct privileged operations can still load the system. Trusted ingress, account provisioning, monitoring, global/edge protection, operational incident response, denial-of-service testing and privacy/retention policy remain mandatory. The feature stays disabled and these limits are not production-ready.
