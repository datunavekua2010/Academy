# Role-specific sign-in enforcement: staging plan

Status: **locally connected prototype only; not deployed**. The owner reports Google is enabled for staging, no other social providers are enabled, CAPTCHA is enabled, and users with multiple Academy roles should be able to switch roles. These are owner reports, not independently verified configuration. The web UI changes on the working branch are not an authorization boundary.

A staging-only browser probe in `scripts/staging-auth-method` can report the authentication method labels for an actual Google sign-in and token refresh, using a dedicated synthetic Google account and a publishable key entered only in the browser. A separate minimal equivalent was supplied for a Codespace because the Arena preview required a traffic token. The owner reported `oauth` at sign-in and after refresh; this is owner-reported, not independently observed. A later aggregated staging catalog query showed password AMR records but no OAuth records at that moment (the test session may have been signed out); it does not independently verify the login. The probe can create a staging Auth user but does not grant Academy roles. It does not prove that all OAuth paths are Google-only, enforce access, or verify production.

A non-deployable local SQL prototype, `supabase/review/role-signin-method-candidate.sql`, and a synthetic full-schema test, `scripts/test-role-signin-method-candidate.mjs`, were prepared. The prototype checks one recognized primary AMR method plus optional TOTP and covers the self-ID branch of `can_view_student` and the direct-role `teacher_classroom_set_capacity` RPC. Its local test passed for selected multi-role, roleless, malformed and mixed-method cases. It also exercises direct raw-attempt RLS reads and student attempt writes in the two simulated methods, plus linked and unrelated parent-summary RPCs. These simulated claims are not verified JWTs and do not prove Google or a real session. It is not a migration or a complete security review and must not be applied remotely as-is. In particular OAuth AMR is not provider-specific, existing sessions and provider paths remain unverified, admin behavior is unchanged, other effective paths and UI method messaging require verification, and real linked multi-role sessions have not been tested.

## Target behavior

A Google-authenticated session with a current student or parent role can use the appropriate student or parent resources; a password-authenticated session with a current teacher role can use teacher resources. Identity alone grants no Academy role or family/teacher relationship. A multi-role user must be able to sign out and authenticate with the other method to use the other role; linking Google and password identities must be verified, not inferred from matching email addresses. Existing role, relationship, data-minimization and revocation checks remain necessary. Admin access, recovery and role-neutral account status need explicit treatment so they are not accidentally locked out or become a bypass.

## Critical prerequisite

Supabase `amr` identifies methods such as `oauth` and `password`, but `oauth` alone does not identify Google. First-provider metadata and linked identities do not prove the provider of the current session. Inspection of the current upstream Auth source found provider information in some audit events, but those event payloads do not provide a documented reliable session binding and database audit logging can be disabled; matching events by user or timestamp would be unsafe, especially with concurrent sign-ins. Source from upstream master does not establish the hosted Auth version or behavior. Before treating an OAuth session as Google, verify a reliable server-side provenance method for this project's enabled authentication flows, including ID-token endpoints, SSO, linking and refresh. A custom access-token hook receives an authentication method, but refresh can report `token_refresh`; do not stamp Google based solely on the current hook event or writable metadata. If Google is the only permitted OAuth provider, any design relying on that fact must verify all relevant provider paths and preserve that invariant in configuration; it is not automatically proven by the Google toggle. Missing or ambiguous provenance must fail closed.

## Candidate provider-specific direction (not deployed)

A possible way around provider-ambiguous Supabase AMR is a separate Google OIDC reauthentication step: generate an unpredictable one-use nonce server-side, verify a Google-signed ID token and nonce, match its stable Google subject to the user's trusted linked Google identity, and atomically bind the proof to that user's verified Supabase session ID. This proves an additional Google authentication for that session; it does not claim the original Supabase OAuth provider was Google. It needs a correct OAuth flow and callback, CSRF/state protection, server-only secrets, session ownership and liveness checks, race-safe nonce consumption and expiry, revocation/sign-out behavior, and effective RLS/RPC coverage. Password sessions must not gain parent access merely by invoking an endpoint; the desired switching behavior and handling of pre-existing sessions must be defined and tested. The implementation must not accept client-provided user IDs, Google subjects, or unverified JWTs as authoritative.

`server/google-identity-proof.ts` verifies signatures against a pinned Google JWKS endpoint and checks issuer, audience/authorized party, fresh timestamps, subject and nonce. `server/google-proof-flow.ts` performs the state/cookie/nonce/PKCE flow and token exchange. `server/google-proof-http-review.ts` connects these to the Worker, authenticates a Supabase token through Auth, and calls privileged proof RPCs; browser callback and proof-status checking are wired behind the `VITE_GOOGLE_PROOF_REVIEW` flag. Worker proof routes fail closed unless explicitly enabled with server-only configuration. Review-only SQL connects the session proof to `has_role`, while separate candidate SQL covers the self-ID path and one direct-role teacher RPC. None of these SQL files has been applied remotely; the flags are not enabled in the checked-in configuration. They do not currently enforce anything on staging or production.

Local synthetic tests check selected RLS/RPC bypass cases, method switching, cookie/nonce/subject mismatch, proof expiration, sign-out and replay. The HTTP callback has also been exercised against the full local SQL prototype through a synthetic service-role RPC adapter: an incorrect signed Google subject failed, the matching subject enabled the parent RPC, the Google session remained unable to use teacher RPCs, a simulated password session could use the teacher RPC but not the parent RPC, and session deletion removed proof access. Teacher lesson-note read/write positive and negative controls also passed. Supabase Auth and Google were mocked, so this is not a real JWT, network or staging test. Local PostgreSQL tests checked replay, sign-out, and one unfinished-start limit race.

The teacher UI previously treated a self-visible teacher role row as proof the current session could use the teacher role; it could display the workspace for a Google session even though protected APIs deny it. The flagged local prototype now checks a server-side effective-teacher-status RPC before loading the workspace; local tests exercise denial, success and RPC failure. The proof candidate also bounds consecutive unfinished starts and callback reads per session, with local tests. Successful completion resets the start counter, and there is no account/IP ingress limit: these partial bounds do not satisfy the production rate-limiting requirement.

A read-only staging catalog check found 14 publicly exposed authenticated-readable Academy tables with RLS enabled and no anonymous SELECT grant. For security-definer RPCs, the known direct-role `teacher_classroom_set_capacity` needs the candidate replacement; the teacher lesson-note write functions authorize indirectly via the pair-lock helper, which calls `has_role`. Separate service-only code/evidence RPCs rely on their trusted gateways and do not automatically inherit the request session method: any runtime exposing those must explicitly enforce the corresponding method and proof. Catalog inspection is not an end-to-end bypass test, and the unchanged admin behavior remains a separate caveat. A staging aggregate query confirmed the single Google identity has matching `provider_id` and identity-data subject; it does not independently validate all Google identity paths. Real Google/Auth/PostgREST/Worker integration, comprehensive effective authorization paths, production-safe rate limiting and cleanup of expired challenges, request-log redaction, proof-expiry UX throughout the student app, rollback, and live-session verification remain outstanding. The SQL must not be applied to staging or production as-is.

## Coverage

Use this checklist to design and review a **new, staged and tested** enforcement migration; do not deploy an unreviewed global change. `academy_private.has_role` is used widely but changing it alone is insufficient. For example, `academy_private.can_view_student` includes a self-ID path, and some self-profile and role reads do not call it. Inspect effective policies and grants, permissive-policy OR combinations, `SECURITY DEFINER` RPCs, triggers, views, storage and any endpoint using privileged credentials. Preserve appropriate identity-only status/profile access deliberately, without allowing private student, parent or teacher data through it. Service-role bypass must never be available to the browser.
