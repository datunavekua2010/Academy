# Achievement gallery: implementation and prerequisites

The gallery exposes the 28 launch requirements and navigation, but **does not award achievements or show earned, locked, or in-progress counts**. An em dash and a muted progress track mean verified progress is unavailable; they do not mean zero. The next-achievement panel cannot identify a closest badge without verified evidence. No attempt or local lesson progress is used as achievement evidence. There are no notifications yet. The gallery is behind the student session gate.

## Why awarding is blocked

- `exercise_attempts.result` is submitted and scored by the browser. A student can alter it. The server currently has no canonical question issuance, answer checking, coverage validation, or verified session-completion event. Homework uses the same unverified engine. Neither the timestamp nor 5 answers alone establish a valid session.
- Lesson completion is device-local and can be modified; no trusted lesson completion event exists.
- Curriculum does not define the required unit-completion or topic-mastery rules, domain/fraction mappings, or assessment coverage and template-diversity expectations in a trusted service. Practice and lesson curriculum use different identifiers, which need an explicit reviewed mapping.
- There are no server-verified assessment events, approved pattern-instance or transfer-problem registry, or multi-step challenge completion records. A client-generated question ID alone is not proof of a correct distinct answer.
- Existing `public.earned_rewards` is protected from authenticated browser writes, has a composite primary key and server default timestamp. It has no evidence reference or guaranteed validated award processor; its rows cannot safely be interpreted as meeting these new rules. Do not treat the current client attempts or legacy reward rows as qualifying evidence.
- No reliable cross-device notification acknowledgement, trusted student timezone policy, or notification delivery protocol exists.

Consequently **all 28** badges are blocked from being awarded. M01 and C01–C07 require verified session or lesson events; M02 requires verified lesson completion; M03–M07 require verified unit/topic completion; A01–A07 require approved mappings and verified mastery assessments; R01–R07 require approved, distinct, server-scored reasoning evidence. Finished/earned and in-progress status, percentages, celebratory notifications, and cross-login persistence cannot be honestly reported until those prerequisites exist.

## Proposed backend design for review (not a migration)

1. Keep the existing curriculum and `earned_rewards` identity rather than introducing a second award table. Extend awards only after designing immutable, auditable evidence references and safe retention/deletion policies. Preserve the `(student_id, achievement_id)` primary key and server timestamp; never allow students to insert, update, or delete awards. Existing rewards need an explicit review/migration policy, not automatic conversion to verified awards.
2. Build a trusted server that issues canonical question instances, checks answers and validates assessment coverage, template diversity, completion rules, and assignment ownership. Record immutable verified events with stable idempotency keys and evidence references. Define what is a valid practice/homework/lesson event before processing; do not elevate existing client attempts or local lesson state into trusted evidence. Persist mappings between lesson and practice units and academy-approved number, geometry, fraction and four domain definitions.
3. Use transactional server-only evaluation and uniqueness constraints to prevent duplicate or concurrent awards. Derive cumulative local dates and Monday–Sunday weeks using an academy-approved IANA timezone and a documented policy for timezone changes. Deduplicate canonical question instances; handle retries and delayed events. Keep awarded tiers permanently even when higher ones are granted. Recalculate any derived progress from verified source events; do not use the existing browser-calculated summaries.
4. Store delivery acknowledgement in a separate own-student record keyed by award, with access narrowly restricted to acknowledging the caller's own existing award, or expose a carefully scoped server RPC. Queue only server-confirmed awards, present them outside active questions, group simultaneous awards, and test retry, concurrency and cross-device acknowledgement.
5. Review grants and RLS alongside existing linked-parent/teacher access; enforce the requested student-only read boundary for this feature without breaking existing policies inadvertently. Test actual authenticated and unauthorized API calls as well as concurrent processors against a non-production project before rollout. A server-side service secret must never be included in the browser.

This document is a proposal, not an applied migration. No database tables, policies or records were modified by this feature. Production deployment and database changes require separate authorization.
