## Migration and selected catalog comparison

The connector `create_migration` interface takes a name and SQL, not a repository version. It recorded the 21 submissions under connector-assigned timestamps; the table above maps those records in application order. The migration table retains one SQL string per record. SHA-256 of each recorded string matched its corresponding local file after removing whole comment-only lines and all whitespace. This is a useful comparison, **not byte equality or a proof of semantic equivalence**: whitespace in string literals is also removed and other catalog objects or subsequent changes are not covered. No history entries were altered and nothing was replayed.

The read-only query in `supabase/review/staging-schema-fingerprint.sql` compared staging PostgreSQL 17 with a clean local PostgreSQL 18 database built by running the 21 local files in order. The following category counts and MD5 digests matched: 188 columns/defaults (`56e0524978570b86de24398f62126b32`), 163 non-not-null constraints (`1325a9709bf2366690e7423d32811f9c`), 59 normalized functions (`87f8d5b30b28c786f3c1f14005083ba9`), 15 policies (`6e4dcd5a33f8539b6566161177601715`), 35 table RLS flags (`1db21905618a30184caeb3889ef6695c`) and five user triggers (`1987dd4317daebf0d32c409c43470906`). PostgreSQL 18's additional not-null constraint records were excluded; column not-null flags were compared. Supabase's extra `public.rls_auto_enable()` event-trigger function was excluded; it is owned by postgres, is security-definer and has anon/authenticated EXECUTE grants, but event-trigger functions are not ordinary callable RPCs. Review its event trigger and privileges in the target. Function normalization has the same whitespace caveat. Index definitions, ownership, grants, role inheritance, default privileges, extension objects, event triggers and exposed schemas were **not** fully compared, so remaining drift is unknown.

To reproduce the local side, run `npm install --prefix .scratch/postgres embedded-postgres@18.7.0-beta.19` then `node scripts/stage1-local-schema-fingerprint.mjs`. It creates and deletes an ephemeral **local** database and prints file hashes and the catalog comparison categories; the SQL file can be run read-only against staging. Remote migration hashes were obtained with `select version,name,encode(sha256(convert_to(regexp_replace(regexp_replace(statements[1], '(?n)^[ \t]*--[^\n]*', '', 'g'), '[[:space:]]+', '', 'g'),'UTF8')),'hex') from supabase_migrations.schema_migrations order by version` and matched the local file order. The comparison assumes one stored statement per migration, which was observed for all 21 records.
