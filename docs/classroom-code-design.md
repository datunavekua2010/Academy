# Reusable classroom codes — proposed design

**Status: classroom capacity, code issuance/redemption, rate limiting, a review-only Worker, and tutor/student controls are implemented locally. Both runtime and browser feature flags default off; nothing is deployed and real authentication remains disabled.** A tutor creates a classroom and sets the code's expiry date and join limit. A reusable code lets an already-linked student join that tutor's classroom. Entering the code does **not** create a tutor–student relationship, grant new access to a student's data, or trigger an additional parent approval. Existing relationships must have been authorized through the separately approved account/linking process. This design builds on the existing review-only classroom migration, not on the local in-memory classroom preview. Do not enable real sign-in, change security settings, apply migrations or deploy without separate authorization.

## Current starting point

- `TEST_ACCOUNT_MODE` is enabled; the app does not authenticate the current student or teacher or connect to Supabase in that mode. The teacher's classroom preview is in memory and has no code enrollment.
- The initial schema has `profiles`, `user_roles`, `parent_students`, and `teacher_students`; with current grants, roles and relationship rows are administrator-managed. A review-only admin link creation function has now been drafted, but account provisioning, independent authorization, link revocation and a safe relationship lifecycle remain separate release blockers; see [account-and-linking-review.md](account-and-linking-review.md).
- `202611230001_classrooms_review.sql` proposes `classrooms` and `classroom_students` plus teacher-only functions. It is **not applied**. Adding a student through those functions requires an existing `teacher_students` link. It has no codes and cannot enroll someone by code.
- An existing `teacher_students` link grants the linked tutor broad access under the initial policies, including the student's profile, grade, assignments, attempts and progress. Classroom joining must not create or expand that link. This authorization and data-integrity model needs review before enabling real users.

## Proposed flow

1. The authenticated tutor creates a classroom. They choose a future code expiry date and the maximum number of students currently in the classroom. The server enforces bounds; exact ranges remain a release decision. Proposed date interpretation: the code remains valid through the end of the chosen date in `Asia/Tbilisi`, displayed clearly, and is stored as an exclusive UTC expiration timestamp.
2. The server generates one high-entropy reusable code. Show it once for copying or sharing; the tutor may revoke it and generate a replacement. Only one unrevoked code per classroom is proposed, with replacement revoking the old one. No code in URLs, browser storage, analytics or application logs.
3. A student signs in to their own account and enters the code. The server verifies the student's role and a **current existing** `teacher_students` relationship with the classroom's owner, as well as classroom status, expiry, revocation and remaining capacity. If any check fails, no membership or relationship is created.
4. If all checks pass, the server inserts membership in one transaction after checking current capacity. The student and tutor can see the membership after it commits. The existing teacher–student relationship is unchanged. No extra parent approval is required for classroom membership.
5. Repeated submissions by an existing class member are idempotent and do not take another place. Revocation, expiration, a full classroom or classroom archiving prevent future code joins. Proposed: the same classroom capacity applies to direct tutor additions as well, and stays in effect if the code expires or is replaced, so no path can overfill the classroom.

**Confirmed capacity semantics:** count students currently in the classroom, not lifetime code uses. Removing a student frees a place. An already-linked student who was removed may use a still-valid code to rejoin when a place is available. Failed attempts and duplicate submissions do not occupy a place. A tutor cannot set a limit below current occupancy; they must remove members first or choose a higher limit.

## Database design and review-only capacity migration

- Reuse `profiles`, `user_roles` and `teacher_students`; do not add a new source of identity or teacher authorization. Code redemption never inserts, updates or deletes `teacher_students`.
- Review the existing proposed `classrooms` and `classroom_students` tables and functions before any deployment. `202611250001_classroom_capacity_review.sql` adds a nullable positive integer `capacity` to `classrooms`, with existing/new rooms uncapped until a tutor sets one. It adds owner-scoped capacity status and revision-checked setter functions, and updates direct-add to check capacity while locking the classroom. Removal already locks the classroom. The opted-in connected UI can fetch code status and current capacity. Occupancy is derived from membership, not a lifetime counter. The review-only code redemption function uses the same classroom lock and capacity checks. Existing rooms need a reviewed migration/default policy before real use.
- `202611270001_classroom_codes_review.sql` adds **`academy_private.classroom_invites`**: an ID, classroom FK, unique cryptographic digest of the code (not the raw code), server expiry timestamp, creation timestamp and optional revocation timestamp. The classroom determines the owning tutor; the client does not supply an authoritative tutor ID. Server constraints validate timestamps; capacity is stored on the classroom, not the invite. Enforce at most one unrevoked code per classroom; generation of a replacement revokes the previous code atomically.
- It adds **`academy_private.classroom_invite_redemptions`**: a unique event ID, invite FK, classroom FK, student FK and server join timestamp. Classroom membership is independently unique by classroom/student; redemption history remains if the membership is removed, so a later valid rejoin can produce a new event. A duplicate submission while the member is already present must not produce a new event. Ensure the invite and redemption refer to the same classroom through a composite foreign key or an equivalently enforced invariant. This is a minimal durable redemption record, not a parent-approval queue; it lets the system audit successful code joins, not calculate live occupancy. Define retention and deletion explicitly before deployment.
- The three issuance/revocation/redemption functions execute only for `service_role`, not `authenticated` or `anon`. They accept an actor ID only from the trusted Worker after Supabase Auth verification and recheck roles, ownership and existing links in SQL. The separate teacher status function uses `auth.uid()` and returns only status/capacity metadata, not code or digest. The Worker generates 130-bit codes and sends only the SHA-256 digest to SQL; the plaintext is shown once and cannot be recovered. A lost code must be replaced.

There is no join-request table or parent-decision table in this design. No changes to `parent_students` or `teacher_students` are needed for code joining. Existing teacher-managed direct additions still require an existing tutor link.

## Security and concurrency

- Generate at least 128 bits of randomness server-side and encode in a human-enterable format, for example 26 base-32 characters grouped for readability. Normalize input consistently; do not treat short guessable codes as authorization. Store a digest of the high-entropy code; never log the plaintext. If shorter codes are selected later, use a server-held keyed digest and strong abuse controls. No signing keys in browser code or the repository.
- Deny direct table reads and writes to anonymous and authenticated clients. Grant only necessary execution on narrowly scoped functions with a fixed empty search path and explicit role/ownership/link checks. A student can join only as their own authenticated identity; a tutor can manage only their own class. Errors for invalid, expired, revoked, exhausted or unauthorized codes should not reveal whether a classroom or student exists.
- Protect redemption with reliable account- and network-level rate limits at a trusted layer that cannot be bypassed through direct RPC access. No raw codes or private student data in monitoring. Review the chosen infrastructure before implementation; local throttling or a client-side timer is not adequate.
- In one transaction use a documented, consistent locking order and recheck current classroom, invitation and teacher–student link, roles, expiry and capacity before inserting or removing membership. Coordinate with link revocation, role removal, code rotation and class archive. Existing link removal must not race into granting unauthorized access; subsequent reads must recheck current authorization. Existing classroom code functions and any new relationship-management operations must follow the same locking protocol.
- The local link-revocation draft removes memberships, including archived classrooms, before removing the link; later relinking does not restore membership. The local role-suspension draft instead retains and hides memberships, and blocks role reinstatement until they are explicitly cleaned up. Both are unapplied and require independent lifecycle, privacy and concurrency review before release.

## Local review decisions and remaining checks

- Code expiry uses the end of the selected date in the Tbilisi time zone; supported date bounds and user experience still need isolated integration review.
- Capacity applies to manual additions as well as code joins and persists after code expiry/revocation. It counts current members; removal frees a place.
- A generated code is shown once; replacement rotates the previous code. Codes never establish tutor–student links and require no additional parental approval.
- The local link-revocation path removes active and archived memberships; relinking does not restore them. The later role-suspension draft retains memberships but blocks role regrant until cleanup. Role removal, retention, deletion and privileged bypasses still require independent review.

## Local capacity implementation and limitations

Run `node scripts/test-classroom-capacity-policy.mjs` and `node scripts/test-classroom-policy.mjs`. These run the SQL only in ephemeral local PGlite. They cover owner/role checks, invalid and stale edits, full-class additions, duplicates, removal freeing a place, unrelated students, archive, and a revoked-link scenario. They do **not** establish multi-connection concurrency behavior or real Supabase security.

If a stored membership no longer has an active tutor link or student role, the existing roster hides it. To avoid an invisible member silently consuming a seat or later causing overcapacity, the draft exposes an owner-only `needs_membership_review` flag and blocks new additions/capacity edits until the membership is resolved through a future reviewed process. It does not disclose that member's identity, delete membership or restore access. Direct authorized removal and duplicate membership retain existing behavior. A review-only admin link-revocation function now removes memberships, including legacy hidden memberships; role revocation, an admin UI and comprehensive lifecycle/security review remain release blockers (see [account-and-linking-review.md](account-and-linking-review.md)). A capacity of null is uncapped; setting one is explicit and cannot be cleared through this draft API. The opted-in connected code issuance form sets capacity; the default preview does not call these APIs.

The review-only SQL implements issuance, expiry, revocation, redemption and audit. It is not applied to any remote database. The example Worker and UI adapters exist, but the existing app is static-only, the Worker is not deployed, the feature flag is off, and authentication remains disabled. No real enrollment has been tested. The Worker ingress and relationship-revocation lifecycle remain release blockers; no production or remote database has been touched.

## Local abuse-protection groundwork and UI

`202611260001_classroom_abuse_review.sql` adds private keyed-digest rate buckets and a service-role-only consume function. It atomically counts both account and network attempts in separate committed calls before a code is parsed or redeemed. The proposed fixed window is 10 attempts per account and 60 per network per 10 minutes; these are tunable security defaults, may affect shared networks, and permit bursts at window boundaries. Counters increment even for blocked attempts. A service-only cleanup function deletes buckets older than 24 hours; a reviewed, monitored scheduled invocation is still needed. Until then data is not automatically deleted. No raw code, account ID or IP is stored in this table.

`server/classroom-code-gateway.ts` provides a framework-neutral handler and Supabase Auth verification / database rate-limit adapters. It requires an injected trusted-network provider and a server-only high-entropy HMAC secret; it never falls back to client-provided forwarding headers. It refuses requests if the secret, identity, network or rate limiter is unavailable, limits before parsing, bounds body size, hashes both identifiers, returns generic join errors and disables caching. A review-only Cloudflare Worker adapter now connects the handler to the service-only redemption function; it is not referenced by the active deployment configuration. It requires a matching allowed origin, runtime Cloudflare metadata and `CF-Connecting-IP`, rejects requests bearing Worker subrequest markers and fails closed without configuration. This is **not proof** of a trusted network boundary: Cloudflare documents that IP headers can be changed in certain Worker subrequests. Independently verify the actual deployment topology, block bypasses, limit request/header/time sizes and validate origin handling before enabling it. See https://developers.cloudflare.com/fundamentals/reference/http-headers/. `getUser` verification requires actual Supabase configuration and an appropriate server client; use secret-manager values only, never `VITE_` or client code. No trusted origin/IP header is assumed by this repo. Account/network limiting cannot stop distributed abuse or shared-network denial of service, and needs independent review, monitoring and operational tuning. The limiter runs after Auth token verification; unauthenticated floods can still burden Auth and must be protected by separately configured Cloudflare/WAF ingress controls.

The classroom page shows expiry/capacity controls and the student profile shows a join form. A same-origin authenticated client adapter connects these to the Worker only when the public build flag `VITE_CLASSROOM_CODES_ENABLED` is `true` and a connected signed-in account is present. The flag is unset by default and test mode remains on, so both controls remain disabled. The controls display success only after the service confirms it. No mock or localStorage enrollment is used. Test mocks do not establish real functionality. The review-only server enforces the code format and expiry; real infrastructure integration remains untested.

Run `node scripts/test-classroom-abuse-policy.mjs` for local service-role access, budget, expiry/reset and cleanup tests, and `npx vitest run tests/classroom-code-gateway.test.ts tests/classroom-code-controls.test.tsx tests/classrooms-ui.test.tsx tests/guest-demo.test.tsx` for gateway/UI checks. These do not exercise real network ingress, real Supabase auth, external deployment, rate-limit bypass or multi-connection database behavior.
