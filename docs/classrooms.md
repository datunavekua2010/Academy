# Classroom management — review, test and rollout

## Actual current state

`სასწავლო მხარდაჭერა` contains classroom controls inside the teacher dashboard. `TEST_ACCOUNT_MODE` is still true and authentication/Supabase are disabled in that mode. The public preview is an **in-memory demonstration**, not an account or real enrollment; data disappears when the component unmounts or the page reloads. Its single test student is explicitly labelled as a test. No classroom data or simulated invite enrollment is saved to browser storage or Supabase. Do not enter real personal information in the public preview.

The connected path is prepared but unusable until the database migration is independently reviewed and applied to an authorized test project and real sign-in is enabled through a separately approved process. The existing connected roster uses `teacher_students` and RLS. The live schema has no classroom/invite tables or functions and no accessible student login identifier or verified account-setup status. The existing future sign-in accepts email and password, but is disabled by test mode. The repository does not establish a canonical official login address. The preview and cards do not invent one.

## Proposed schema, not applied

`supabase/migrations/202611230001_classrooms_review.sql` adds `classrooms` with teacher profile FK, bounded name, optional grade and description, archive timestamp, server timestamps and revision; `classroom_students` links profiles with a composite unique key and supports multiple classrooms per student. Restrictive FKs prevent account deletions from silently erasing membership/classroom history; an explicit retention and deletion strategy is needed before rollout. Archiving only changes the classroom timestamp, leaving memberships, student accounts, parent links, assignments and learning data unchanged. It is read-only afterward. Removal deletes only the classroom membership.

RLS is enabled but no direct table grants or policies are supplied; direct access is denied. Six `SECURITY DEFINER` RPCs use an empty search path and check the actual `auth.uid()`, teacher role and classroom ownership. List/count and roster expose only students with a current teacher-student link and student role. Add/remove require that current assignment; `ON CONFLICT DO NOTHING` prevents duplicate membership; archive and add/remove lock the classroom row to serialize changes. Classroom edits and archive require a revision. A revoked teacher/student relationship hides the student from roster/counts without deleting the membership. Membership revocation races and transaction isolation need dedicated security/concurrency testing in the real deployment environment. Existing links are never created or modified by these RPCs.

## Invite codes and login cards

Code issuance, expiry, redemption and rate-limit infrastructure now exist as local review-only code; they are not deployed or enabled. Public signup remains unimplemented. The selected model is a reusable tutor-controlled code, with teacher-set expiry and current classroom capacity (removing a student frees a place), usable only by a student already authorized and linked to that tutor. Joining a classroom does not itself create a `teacher_students` relationship or require a new parent approval. See [classroom-code-design.md](classroom-code-design.md) for the proposed schema, remaining product decisions and safeguards; none of it has been deployed. The local implementation includes authenticated redemption, cryptographic code generation, expiry/revocation, atomic membership writes and account/network rate limits; trusted ingress and bypass prevention still require independent validation. Six-character codes have a limited search space and cannot be treated as credentials. These capabilities must be tested for rate limiting, invalid/revoked/expired codes, and simultaneous redemption on a dedicated environment before production use.

Cards display name, classroom and a clear **unknown account status**. No database ID, email, password, hash, token, secret, fake login URL or fake credential is printed. The administrator is asked to verify/complete account setup and provide the approved login address. The system cannot distinguish valid accounts from incomplete ones until an authorized identity/setup-status API and official URL are defined; therefore no card claims either state. Card selection is revalidated against the backend immediately before printing on the connected path, but a printout cannot be recalled if access is subsequently revoked. Handle the paper/PDF as personal information. The browser print dialog provides Save as PDF where supported; no PDF library is installed and no separate PDF generation service was added.

The print portal renders only selected cards, on A4 with dashed cut boundaries and page-break avoidance. Browser print capabilities vary. See tests for actual verification; this is not a guarantee for all browsers, printers, very long names or page settings.

## Setup and verification

Do not apply this migration or enable sign-in without approval. For an isolated test project only, review the migration's function ownership and privileges, retention/deletion and existing relationship authorization; provision test-only users/roles/links through the trusted administrator, use only the existing `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`, and keep service-role keys out of client code. After approval, apply migrations using the project's normal controlled migration process, configure authenticated sessions, and run independent real Supabase/PostgREST RLS, multi-session concurrency, privilege and print tests. There is no new environment variable. No production data was written.

Run `node scripts/test-classroom-policy.mjs` for local PGlite authorization/constraint checks and `npx vitest run tests/classrooms-ui.test.tsx tests/classrooms-data.test.ts` for UI/data checks. These are not a substitute for actual Supabase end-to-end or multi-connection concurrency tests. Rolling back after a future deployment requires an explicit export/retention decision: dropping classroom tables destroys classroom membership records, even though it does not delete student accounts.

## Capacity groundwork (local only)

`202611250001_classroom_capacity_review.sql` is a local review-only draft adding classroom capacity and owner-scoped checks to the existing proposed classroom migration. It is not deployed; code issuance can set its capacity only when the connected feature is enabled, and classroom-code issuance and redemption are implemented separately. See [classroom-code-design.md](classroom-code-design.md) for the fail-closed revoked-link behavior and release blockers. `node scripts/test-classroom-capacity-policy.mjs` verifies local PGlite authorization and single-session behavior only; real multi-connection and security tests remain necessary.

## Code interface and abuse-protection groundwork (local only)

The classroom code controls and student join form are present but disabled by default. A review-only Worker, server-only issue/redeem functions and local rate limiter are implemented but not deployed or proven bypass-proof. See [classroom-code-design.md](classroom-code-design.md) for the trusted-ingress, cleanup, operational and testing prerequisites. No remote database or authentication changes were made.
