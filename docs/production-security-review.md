# Production security review — draft, do not deploy

## Scope and findings

Only local files changed. No Supabase or Cloudflare settings, migrations or deployments were changed. Unconfigured production builds fail closed, development defaults to the local test account, and `VITE_ACCOUNT_MODE=connected` explicitly selects connected mode; signup, OAuth, recovery, admin and parent features remain gated. The initial database baseline gives linked parents full attempt JSON; later migrations narrow parent-only access but are not on the existing project. Verify actual RLS, ACLs, default privileges, memberships, owners, exposed schemas, `SECURITY DEFINER` functions, triggers and storage policies in the target before planning a rollout. Service roles and owners can bypass RLS. Subscription entitlements and server-verified student scoring do not exist. Child-data notice, consent, retention/deletion and independent privacy/security review are release blockers.

A heuristic scan of 865 working-tree text files found no common embedded secrets; it excluded dependencies, binary files, generated outputs and Git history, and is not proof. Scan Git history and the deployed bundle separately with an approved secret scanner. `SUPABASE_SERVICE_ROLE_KEY` is used only by the separate, disabled classroom Worker draft, not the browser. Rotate any actual exposed secret immediately. No `.env` files were present locally. Never put service-role, OAuth client secret, Turnstile secret or payment webhook secret in any `VITE_`, `PUBLIC_` or `NEXT_PUBLIC_` variable, source code or chat.

In the explicitly approved test project `wxxgwayrieasrzngpuul`, read-only catalog checks found 17 public tables with RLS enabled, no storage buckets or storage policies, and only the first three migrations applied. Its Academy security-definer functions have fixed search paths and no anon execute grants. Supabase also has a `public.rls_auto_enable()` event-trigger function with broad execute grants; event-trigger functions cannot be invoked as regular SQL functions. Review its owner, trigger behavior and grants in the actual target, rather than assuming this alone is a vulnerability. Test project is not production-ready; no real child data.

## Environment inventory

The deployed `wrangler.toml` serves static assets only; it has no runtime Worker environment and no API endpoint. Vite `VITE_` values are public build-time values embedded in JS. For a future reviewed account build, set **build variables** `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_AUTH_CALLBACK_ORIGIN` (exact HTTPS origin without a trailing slash), and `VITE_TURNSTILE_SITE_KEY` (public site key). Connected mode additionally requires `VITE_ACCOUNT_MODE=connected`; parent and administrator screens require `VITE_PARENT_ENABLED=true` and `VITE_ADMIN_ENABLED=true` respectively, after their database and security prerequisites have been verified. These UI switches are not authorization. `VITE_ACCOUNT_SIGNUP_REVIEW`, `VITE_PASSWORD_RECOVERY_ENABLED`, `VITE_GOOGLE_AUTH_REVIEW`, `VITE_CLASSROOM_CODES_ENABLED`, and `VITE_TURNSTILE_REVIEW` are opt-in review flags; leave them unset in production until reviewed. Connected password forms fail closed without the site key/working verification route, even if the review flag is absent.

The **separate** `wrangler.auth-review.toml.example` requires non-secret `TURNSTILE_REVIEW_ENABLED` (default `false`) and `TURNSTILE_ALLOWED_ORIGIN` (exact HTTPS origin without trailing slash), plus `TURNSTILE_WORKER_SECRET` stored as a Cloudflare Worker secret. `ASSETS` is a binding, not an env string. This Worker is not routed by the current config. The separate classroom example uses `SUPABASE_URL`, `CLASSROOM_ALLOWED_ORIGIN`, `CLASSROOM_CODES_ENABLED`, `ASSETS` and server secrets `SUPABASE_SERVICE_ROLE_KEY` and `CLASSROOM_RATE_KEY`. These are not necessary for the current static preview. No payment webhook variables are implemented or required yet. Never add privileged keys to the static build.

## Redirect and Turnstile review

Email signup, password recovery and Google OAuth construct same-origin callbacks. In connected mode the callback is additionally pinned to the exact HTTPS `VITE_AUTH_CALLBACK_ORIGIN` and root path. Configure Supabase's own exact redirect allowlist and Site URL independently; do not use wildcards. Configure separate test and production Google OAuth redirect URLs and credentials. Test scanners, expiry, PKCE, account switching and same-email identity linking. The helper is client-side defense in depth, not a replacement for server-side redirect restrictions.

The review password login (student, teacher, parent and admin), signup and recovery request forms use **two different Turnstile tokens**: a Worker validates one with Siteverify and Supabase receives the other in `captchaToken`. Cloudflare tokens are single-use; one token cannot reliably be verified twice. The Worker precheck is not an authorization token and can be bypassed by calling Supabase directly. Enabling Supabase Auth's own CAPTCHA enforcement with the Turnstile secret is essential for the real boundary, as is independent rate limiting. Google OAuth is not protected by these password form checks; assess provider-level abuse controls and Supabase OAuth behavior separately. A Google account can be created without going through the adult-checkbox form; no identity, age, consent, role or parent authority is inferred. If challenge widgets, precheck, site key, Supabase enforcement or verifier are missing or broken, do not enable real sign-in. The Worker has no distributed rate limiting and needs ingress, logging, accessibility and abuse review. No real verification or authentication was tested.

## RLS SQL snapshot

`supabase/review/fresh-security-schema.sql` is a single transaction generated from the 21 local review migrations. It refuses any Auth users, public tables/views or existing `academy_private` schema, and therefore **cannot upgrade either current project**. It deliberately omits curriculum seed and migration-history tracking. Do not paste into production; do not replay it over existing tables. `node scripts/build-fresh-security-review.mjs` regenerates it when the reviewed migration chain is unchanged; `node scripts/test-fresh-security-review.mjs` checks the guard, RLS and selected grants on synthetic PGlite only.

Policies differ by table: curriculum is authenticated-readable; roles, grades, links, rewards and private records are not client-writable; student attempts use owner/role checks; teacher and parent access is relationship-scoped and much functionality is narrowly exposed via checked RPCs. Operations with no policy/grant are intentionally denied—adding generic CRUD policies would weaken protection. The script does not cover unknown pre-existing tables, views, existing policies, roles or buckets, and does not make the review migrations production-safe. Plan separately reviewed incremental migrations for the actual existing project; `REVOKE`/RLS does not constrain BYPASSRLS or owners.

## Payment webhook scaffold — unavailable

`server/payment-webhook-review.ts` is unrouted and returns 503 unconditionally. It is not a payment integration. Its typed RPC helper points to an intentionally uninstalled mock RPC in `supabase/review/payment-webhook-mock.sql`. The mock accepts only `review_only` synthetic events, stores a mock status that the app never uses, and cannot represent a real subscription. `node scripts/test-payment-webhook-mock.mjs` tests selected sequential duplicate, conflict, ordering, mapping, rollback and privilege cases with synthetic PGlite; it is not real provider validation or a concurrency proof. Do not implement a permissive signature placeholder or a browser-controlled status update. Choose a provider first, validate its signature over bounded **raw bytes** and timestamp with its official verification mechanism and secret, handle replay/rotation, resolve provider customers to users using trusted server-owned mappings, and reject unrecognized products/statuses. In one database transaction, reserve a unique `(provider,event_id)` and apply only an authorized, correctly ordered state transition; return duplicate only if the same event was already committed. A separate dedup check then an update is unsafe. Handle retries, out-of-order events, provider version semantics, refunds/cancellations, reconciliation and access revocation. A service-only RPC should atomically perform both operations with narrow grants; the Worker may use `createClient(SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY, {auth:{persistSession:false,autoRefreshToken:false}})` and call only that RPC. Never forward the key or allow a client to choose a user or plan. The mock stores deduplication and mock status in a single database transaction, but no real subscription/entitlement database or verified provider adapter exists yet. Keep payments deferred until a provider and legal/business setup are chosen.

## Headers

`public/_headers` applies to Cloudflare Workers **static asset** responses; custom Worker/API responses must set their own headers. It uses a restrictive script policy and allows Turnstile plus the two known Supabase project origins for testing. Before deployment, confirm the intended production origin, remove test origins from the production policy and validate all real routes, OAuth, PDF downloads, Turnstile, inline styles, realtime and embedding. `style-src 'unsafe-inline'` is currently necessary for existing React styles and is a residual risk; eliminate it when styles are refactored. `frame-ancestors 'none'`/`X-Frame-Options: DENY` prevents embedding, including embedded previews; use a deliberately separate preview policy if needed. HSTS omits `includeSubDomains` and preload pending domain review. Do not deploy this header file without browser/CSP report testing and explicit approval.
